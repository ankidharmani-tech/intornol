## Project Context (in case this is the only doc you're reading right now)

**What we're building:** a citizen types a civic task in plain language (e.g. "I want
to start a home-based food business in Thane"). The system asks 3–4 clarifying
questions, then returns an ordered, personalized roadmap of every form/document/fee/
office involved, sourced from real official government pages. PS ID: PSWB02.

**The pipeline, end to end:**
```
task text --> [1: match to relevant services] --> clarifying Qs -->
[2: query the graph for the relevant dependency subgraph] -->
[3: put that subgraph in valid step order] --> roadmap shown to citizen
```
Step 1 = embeddings + cosine similarity (below).
Step 2 = Neo4j (below).
Step 3 = topological sort (below).

## 1. Neo4j — what it actually is and why we're using it

**The one-sentence version to say out loud:** *"Neo4j is a database built specifically
to store things-and-relationships, so asking 'what does X depend on, going back five
steps' is one query instead of five joins."*

**What's actually happening:** A normal (relational/SQL) database stores rows in
tables. To find "everything required before FSSAI registration, and everything
required before THAT," you'd have to join the requirements table to itself
repeatedly — and you don't know in advance how many times, because dependency
chains vary in length.

A **graph database** stores data as it naturally is for this problem:
- **Nodes** — a thing (a Service, a Document, an Office). Each node has a *label*
  (its type) and *properties* (key-value data — name, fee, jurisdiction, etc.)
- **Relationships** — a directed, typed connection between two nodes (e.g.
  `(:Service)-[:REQUIRES]->(:Document)`), which can *also* carry properties.

This is called the **property graph model**. Neo4j is the most widely used database
built on it.

**Cypher — the query language.** It's designed to visually resemble the graph
pattern you're describing — parentheses are nodes, arrows are relationships:

```cypher
// Find every document required for FSSAI Basic Registration in Thane, Maharashtra
MATCH (s:Service {id: "svc_fssai_basic_reg"})-[:REQUIRES]->(d:Document)
RETURN d.name, d.description
```

```cypher
// Find the FULL dependency chain leading up to a target service —
// this is the query that actually builds your roadmap.
// The *1..6 means "follow this relationship 1 to 6 times" — a variable-length
// path, which is the whole reason a graph DB beats a normal table here.
MATCH path = (start:Service)-[:PREREQUISITE_FOR*1..6]->(target:Service {id: "svc_fssai_basic_reg"})
WHERE start.applicable_region IN ["Maharashtra", null]
RETURN path
```

**AuraDB Free (what you'll actually connect to):** it's Neo4j hosted in the cloud —
you sign up, get a connection URI + username + password, and connect from Python
with the `neo4j` driver over the Bolt protocol. No server to install or manage.

```python
from neo4j import GraphDatabase
driver = GraphDatabase.driver(URI, auth=(USERNAME, PASSWORD))
with driver.session() as session:
    result = session.run("MATCH (s:Service) RETURN s LIMIT 5")
    for record in result:
        print(record["s"])
```

**If a judge asks "why not just use a normal database":** because the number of
steps between "what the citizen typed" and "the final required document" is
*unknown and variable* — some tasks are 2 steps deep, some are 6. A graph
database answers "how deep does this go" natively; a relational database needs
you to guess the number of joins in advance.

## 2. Do we need RAG? (Short answer: no — we need retrieval, not RAG)

**Say this confidently if asked:** *"We use retrieval — matching a task to relevant
services — but the actual answer isn't generated by an LLM, it's computed
deterministically by a graph traversal. That's intentional: it means we can't
hallucinate a wrong step order, because there's no generation step in the final
answer."*

**RAG (Retrieval-Augmented Generation)** usually means: retrieve some relevant text
chunks, then have an LLM *write* a free-text answer using them as context. We only
use the *retrieval* half. What comes after retrieval — the roadmap itself — is
built by graph traversal + topological sort (below), not by an LLM writing prose.
This is a genuine architectural strength, not a shortcut — say it like one.

## 3. Embeddings & Sentence-Transformers — how "matching by meaning" works

**The one-sentence version:** *"We convert each service description into a list of
numbers that represents its meaning, do the same for the citizen's typed task, and
then measure how close those two lists of numbers are — closer numbers means more
similar meaning, even if the words used are totally different."*

**What is a vector embedding?**
A fixed-length list of numbers (e.g. 384 of them, for the model we're using) that
represents a piece of text such that texts with similar *meaning* produce lists of
numbers that are close together — even if they don't share any of the same words.
Example: "start a food stall" and "open a small eatery" should land close together
in this number-space, even though they share almost no vocabulary.

**How sentence-transformers actually produces this:**
It's a neural network (built on the same transformer architecture as GPT/BERT)
that has been specifically trained so that sentence-level meaning, not just
word-level meaning, gets captured in the output numbers. During training, it's
shown pairs of sentences that mean the same thing and pairs that mean different
things, and adjusted repeatedly until similar-meaning pairs produce close-together
number-lists and different-meaning pairs produce far-apart ones. We don't train
this ourselves — we use an already-trained model (`all-MiniLM-L6-v2` is a good
free, fast choice) and just feed text into it.

```python
from sentence_transformers import SentenceTransformer
model = SentenceTransformer('all-MiniLM-L6-v2')
vector = model.encode("I want to start a home-based food business")
# vector is now a list of 384 numbers
```

**Cosine similarity — how we measure "how close":**
Once you have two vectors, cosine similarity measures the *angle* between them
(not their length/magnitude) — giving a score from -1 (opposite meaning) to 1
(identical meaning). Formula: dot product of the two vectors, divided by the
product of their magnitudes.

**Worked tiny example (so you can explain the actual math if pushed):**
Pretend our vectors only have 2 numbers instead of 384, just to see the arithmetic:
- Vector A ("food business"): `[0.8, 0.6]`
- Vector B ("food stall"): `[0.7, 0.7]`
- Vector C ("passport renewal"): `[-0.2, 0.9]`

Cosine similarity(A, B) = (0.8×0.7 + 0.6×0.7) / (√(0.8²+0.6²) × √(0.7²+0.7²))
= (0.56 + 0.42) / (1.0 × 0.99) ≈ **0.99** → very similar, as expected.

Cosine similarity(A, C) = (0.8×-0.2 + 0.6×0.9) / (1.0 × √(0.04+0.81))
= (-0.16 + 0.54) / 0.92 ≈ **0.41** → much less similar, also as expected.

**The actual pipeline we run:**
1. At ingestion time: embed each service's description once, store the vector
   alongside the node (or in a simple in-memory list/dict — no vector database
   needed at our scale of ~50–100 services).
2. At query time: embed the citizen's typed task with the *same* model.
3. Compute cosine similarity between the query vector and every stored service
   vector (`numpy` can do this for 100 vectors in milliseconds).
4. Take the top-k highest-scoring services as "relevant" → feed their IDs into
   the Neo4j query above.

```python
import numpy as np
def cosine_similarity(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

scores = [(service_id, cosine_similarity(query_vec, vec)) for service_id, vec in service_vectors.items()]
top_matches = sorted(scores, key=lambda x: x[1], reverse=True)[:5]
```

## 4. Topological Sort — turning a dependency graph into an ordered list

**The one-sentence version:** *"It's the same logic as a course prerequisite chart —
you can't take Data Structures before Intro to Programming — applied to government
forms instead of courses."*

**What it does:** given a directed graph where an edge `A → B` means "A must happen
before B," a topological sort produces ONE valid linear ordering that respects every
such constraint. It only works on a **DAG** (Directed Acyclic Graph — no circular
dependencies), which our service-dependency graph naturally is (you'd never have
"Document X requires Document X").

```python
import networkx as nx
G = nx.DiGraph()
G.add_edge("aadhaar_card", "address_proof_check")
G.add_edge("address_proof_check", "fssai_registration")
G.add_edge("fssai_registration", "trade_license")

ordered_steps = list(nx.topological_sort(G))
# ['aadhaar_card', 'address_proof_check', 'fssai_registration', 'trade_license']
```

We pull the *matched subgraph* (just the nodes relevant to this specific citizen's
task) out of Neo4j, hand just that small subgraph to `networkx`, and run this
one line to get the roadmap order. Neo4j holds everything at scale; `networkx`
does the one-line ordering math on the small relevant slice.

## 5. LLM Extraction — turning messy government text into structured graph data

**The one-sentence version:** *"We give the LLM the raw text from an official page
plus a strict template of what fields we need, and tell it to only fill in what's
explicitly stated — never invent anything."*

This is called **structured extraction** — a narrower, more reliable task than
open-ended chat, because the LLM's job is just "find and format," not "compose."

Example prompt shape (adapt as needed):
```
You will be given raw text from an official Indian government service page.
Extract ONLY information explicitly present in the text into this JSON shape:
{ "name": "", "documents_required": [], "fee": null, "processing_days": null,
  "office_name": null, "official_source_url": "" }
If a field isn't mentioned, use null — do not guess or infer a value.
Text: <paste source text here>
```

Every extracted record gets a `confidence` score and goes into the **review queue**
before it's trusted — a human (your admin dashboard) checks it against the source
before it's used to build a citizen's roadmap. This is why we can honestly claim
"grounded, not hallucinated."

- "Why a graph database instead of a normal one?" → *"Dependency chains have unknown, variable depth — that's a native graph-DB query, not an unbounded number of SQL joins."*
- "How do you match a vague sentence to the right service?" → *"Sentence embeddings plus cosine similarity — same-meaning text lands close together in vector space even with completely different words."*
- "How do you order the steps correctly?" → *"Topological sort on the dependency subgraph — same logic as course prerequisite planning."*
- "How do you avoid the LLM making things up?" → *"Extraction is constrained to explicitly-stated facts only, scored by confidence, and reviewed by a human before it's trusted."*
